# API error response contract

**Status:** Common error envelope implemented in both backends; shared HTTP parity fixtures and initial integration coverage merged in PR #14; client compatibility audit in progress  
**Applies to:** Spring Boot and Laravel implementations of `/api/v1`  
**Purpose:** Define one client-facing error representation before changing either backend's runtime behavior.

## Current behavior

The two implementations now normalize covered errors to the common envelope. Legacy framework-specific fields may still appear on unconverted paths and must remain tolerated during rollout:

- Covered Laravel and Spring paths now emit the shared `code` and `message` fields; validation may also include `errors`.
- Legacy framework-specific fields may still appear on unconverted paths and must remain tolerated during rollout.
- Authentication failures can be generated by security middleware/filter chains before controller execution, so both security layers require direct tests.

Do not treat the error formats as equivalent until both implementations and their security layers are covered by contract tests.

## Proposed JSON envelope

All API errors should use this shape:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "The request contains invalid fields.",
  "errors": {
    "answers.0.timeSpentMs": [
      "The time spent must be a non-negative integer."
    ]
  },
  "traceId": "optional-correlation-id"
}
```

### Field rules

| Field | Required | Contract |
|---|---:|---|
| `code` | Yes | Stable machine-readable uppercase identifier; clients must not branch on message text. |
| `message` | Yes | Safe, human-readable summary; must not expose stack traces, SQL, tokens, or internal exception details. |
| `errors` | No | Object keyed by request field/path; each value is an array of validation messages. Omit when there are no field errors. |
| `traceId` | No | Correlation identifier when available; never use it as an authorization or user identifier. |

Unknown fields must be tolerated by clients for forward compatibility. Error bodies must not contain secrets or raw exception details.

## Status and code mapping

| HTTP status | Code | Usage |
|---:|---|---|
| 400 | `BAD_REQUEST` | Malformed request or invalid request semantics not represented as field validation. |
| 401 | `UNAUTHENTICATED` | Missing, invalid, or expired bearer token. |
| 403 | `FORBIDDEN` | Authenticated principal lacks permission. |
| 404 | `NOT_FOUND` | Resource does not exist or is not visible to the caller. |
| 409 | `CONFLICT` | State conflict, such as submitting an already closed quiz attempt. |
| 422 | `VALIDATION_ERROR` | Syntactically valid request with field-level validation failures, or a documented domain validation failure. |
| 429 | `RATE_LIMITED` | Rate limit exceeded. |
| 500 | `INTERNAL_ERROR` | Unexpected server failure; response must not reveal implementation details. |

The mapping is implemented for the common statuses covered by the current handlers. Less common framework-generated statuses still require parity verification. Preserve existing status semantics unless a separately reviewed API compatibility change is approved.

## Implementation requirements

1. Implemented in Spring MVC exception handling and Spring Security's authentication-entry-point and access-denied handling. Spring MVC response tests and production-filter-chain tests for missing/invalid bearer tokens are merged in PR #14. Spring method security is enabled and a production-filter-chain test now verifies a principal without `content.publish` receives the common 403 envelope; an authorized principal is allowed. The permission test seeds the authenticated principal with Spring Security's test support, so it validates authorization enforcement and error handling but does not yet exercise permission loading from a persisted bearer token.
2. Implemented in Laravel's API exception rendering for validation, authentication, authorization, HTTP exceptions, not-found, throttling status mapping, and unexpected failures. Laravel HTTP feature tests cover authentication, permission denial, validation, bad request, not-found, and unexpected exceptions in PR #14.
3. Status-to-code mapping is implemented for the documented statuses. Add parity tests to prove status preservation across framework-specific exceptions.
4. Validation field paths and message arrays are included; tests must verify they do not leak rejected secrets or request bodies.
5. Correlation IDs are not emitted by the initial implementation; add a trusted request correlation strategy in a follow-up before relying on `traceId`.
6. Keep successful response payloads unchanged.
7. Verify that Android and web clients do not depend on framework-specific error fields before switching the API v1 runtime format. If clients do depend on them, deploy a compatibility reader first or version the breaking behavior.

## Required parity tests

The shared status-to-code fixture is maintained in `docs/api/error-response-parity.json`. Spring Boot and Laravel test suites both read this file so status mapping changes are checked against the same expected values.

Run the same cases against both backend implementations and compare status plus JSON semantics:

- malformed JSON and invalid request fields;
- shared status-to-code fixture cases (400, 401, 403, 404, 409, 422, 429, 500, and 503);
- missing, invalid, and expired bearer token;
- authenticated user without permission (including persisted-token permission loading in both runtimes);
- missing or unpublished resource;
- duplicate or already-completed quiz submission;
- rate-limit rejection;
- unexpected exception.

Assertions should verify required envelope fields, optional field behavior, no stack trace/SQL/token leakage, and stable machine-readable codes. Test security-filter and middleware-generated responses, not only controller exceptions.

## Rollout sequence

1. Added shared OpenAPI schema and reusable error responses for the documented statuses.
2. Added backend error mappers and initial Spring unit tests; full integration and Laravel parity tests remain outstanding.
3. Shared status-code fixtures, Spring MVC/filter-chain tests, and Laravel HTTP feature tests are merged in PR #14; not every documented scenario is yet exercised through both runtimes.
4. Android compatibility parsing is centralized; this repository contains no web client implementation to audit.
5. Spring permission-denial enforcement is now covered at the method-security/filter-chain boundary. Complete persisted-token permission parity, cross-runtime expired-token behavior and rate-limit parity, then run all CI workflows before considering any runtime rollout.

## Exit criteria

- Every documented error response references the common schema.
- Both backend implementations return the same status and envelope semantics for the parity matrix.
- Security-generated errors are covered, including Spring method-security denial and missing/invalid bearer-token authentication paths. Persisted-token permission loading remains to be verified.
- Android and web clients handle the common envelope.
- CI fails when the two implementations diverge on the parity fixtures.

The initial implementation is in progress. Do not treat the contract as production-ready until cross-backend integration tests pass and Android/web client compatibility has been verified.
